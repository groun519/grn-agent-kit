# 프로젝트 작업 체크포인트

사용자가 현재 상태와 다음 작업을 한눈에 보고 항목별 완료 여부를 직접 체크할 수 있는 작업 원장을 만든다. 사용자 언어와 기존 문서의 형식을 따른다.

## 범위와 기준 문서

- 새 문서를 만들거나 기존 CP의 범위·순서·상태를 갱신하는 작업에 사용한다. 사용자가 초안이나 제안만 요청하면 저장하지 않고 초안으로 전달한다.
- 현재 요청, 기존 CP, 관련 설계·코드·검증 기록을 필요한 만큼 읽는다. 이미 확인한 근거를 재사용하되 현재 상태에 중요한 변경 가능성은 확인한다.
- 참조 문서는 형식과 정보 배치의 예시로 사용한다. 프로젝트명, CP 수, 아키텍처, Git 정책, 사용자 승인 절차를 다른 프로젝트의 규칙으로 복사하지 않는다.
- CP 작성·갱신 요청만으로 코드 구현, 의존성 설치, 빌드, 배포, Git 작업을 시작하지 않는다. 기존 기록과 읽기 전용 확인만으로 불확실한 상태는 미확인으로 남긴다.
- 기존 CP가 있으면 해당 문서를 갱신한다. 사용자가 새 문서를 요청한 경우를 제외하고 중복 원장을 만들지 않는다.

## 단계 나누기

먼저 사용자가 얻으려는 실제 결과와 현재 구현 범위를 파악한다. 최소한의 유용한 동작을 먼저 완성하고, 그 결과에 의존하는 확장·복구·배포·운영 작업을 뒤에 배치한다. 연구와 설계가 구현·실행을 대체하지 않게 한다.

각 CP는 독립적으로 설명할 수 있는 결과와 완료 기준을 가진다. 단계 수는 작업 규모와 의존 관계에 맞춘다. 불확실한 요구와 선택적 확장을 첫 단계의 필수 조건으로 묶지 않는다.

- 제목은 `CP1 환경 연결`처럼 구체적인 작업 범위를 드러낸다.
- 체크 항목 하나는 확인 가능한 결과 하나를 담는다. 구현과 실행 검증이 각각 남을 수 있으면 항목을 나눈다.
- 완료 기준은 기능 이름을 반복하지 말고 어떤 입력·행동·출력 또는 관찰 결과로 통과를 판단할지 쓴다.
- 수치 기준이 정해지지 않았다면 먼저 그 기준을 정하는 항목을 둔다. 근거 없이 성능 수치나 일정을 약속하지 않는다.

## 체크 상태와 검증

- `- [x]`는 해당 항목이 요구하는 구현과 확인이 끝났다는 근거가 있을 때만 사용한다. 그 외에는 `- [ ]`로 둔다.
- 코드 존재나 소스 검토로 빌드·통합 실행·제품 환경의 성공을 체크하지 않는다. 작은 예제의 성공 범위를 실제 제품 전체로 넓히지 않는다.
- 필요한 검증 층만 구분한다. 예: 소스 검토, 자동 검사, 빌드, Editor·PIE, 실제 사용자 화면, 패키지 실행. 모든 프로젝트에 이 목록 전체를 강제하지 않는다.
- 검증 기록에는 날짜, 대상 환경·버전, 결과, 근거 링크나 파일을 간결하게 남긴다. 근거가 과거 기록이면 해당 시점의 확인임을 표시한다.
- 전체 CP는 완료 기준이 충족되어야 완료다. 일부 체크가 끝났으면 진행 중, 구현 후 필요한 확인이 남았으면 검증 대기로 표시한다.
- 사용자 검수·승인이 실제 요구인 경우에만 구현·실행 검증과 별도로 표시한다. 새 승인 절차를 만들지 않는다.

## 문서 구성

새 문서 작성 시 [체크포인트 형식](references/checkpoint-format.md)을 읽고 프로젝트 규모에 맞게 적용한다. 기본 구성은 목적 한 문단, 현재 상태와 다음 작업, 진행 현황표, CP별 목표·체크박스·완료 기준이다. 구조 방향, 검증 기록, 후속 확장, 근거는 이해에 필요할 때 덧붙인다.

보기 좋은 편집 가능한 문서를 만든다. 네이티브 제목·표·체크리스트를 사용하고, 체크박스를 이미지나 코드 블록으로 대체하지 않는다. 반복되는 상태 요약과 각 CP의 실제 체크 상태가 일치하도록 검토한다.

## 기존 문서 갱신

기존 CP 번호·제목·체크 상태·메모·검증 기록을 먼저 읽는다. 현재 요청에 필요한 부분만 변경하고 완료 이력을 보존한다.

- 항목을 분할하거나 범위를 넓히면 기존 완료 체크를 새 범위에 그대로 복사하지 않는다.
- 재정렬이 필요해도 가능하면 CP 식별자를 유지한다. 번호를 바꾸면 이전 번호와 새 번호의 대응을 남긴다.
- 회귀나 환경 변경으로 근거가 유효하지 않으면 이유를 남기고 상태를 재평가한다. 근거 없이 완료를 해제하거나 유지하지 않는다.
- 기존 문서의 작업 규칙은 현재 프로젝트에 적용되는지 확인한다. 표에 적힌 규칙만으로 새 실행 권한이나 승인 조건을 만들지 않는다.

## 저장과 확인

- ChatGPT Page는 채팅 답변이나 일반 게시물이 아니라, 제목·표·체크박스를 직접 편집하고 이후 대화에서 계속 갱신할 수 있는 독립 문서다.
- 사용자가 CP를 `Page로 저장`, `게시물로 올리기`, `작업 원장으로 만들기`처럼 명시적으로 요청하면 `pages:write-page` 스킬을 적용해 ChatGPT Page로 생성한다. 계획·초안만 요청한 경우에는 Page 생성 권한으로 해석하지 않는다.
- 새 Page의 목적지, 부모 또는 Space가 지정되지 않았다면 별도 질문 없이 부모 없는 비공개 Page로 만든다. 특정 Page나 Space가 지정되었다면 해당 대상을 먼저 읽고 그 위치를 사용한다.
- Page에는 네이티브 제목·제목 블록·표·체크리스트를 사용한다. 저장 후 다시 읽어 구조와 상태를 확인하고, 최종 응답에 사용자가 열 수 있는 Page 링크를 반환한다.
- 사용자가 지정한 Page나 파일을 사용하고 기존 프로젝트 문서 관례를 존중한다. 열린 Page나 형식 예시 링크만으로 그 원본을 편집할 권한이 생기는 것은 아니다.
- ChatGPT Page를 만들거나 편집할 때는 사용 가능한 `pages:write-page` 스킬을 적용하고 현재 Page 도구 스키마를 따른다. 사용할 수 없으면 그 한계를 알리고 같은 형식의 초안을 제공하며 Page가 저장되었다고 주장하지 않는다.
- Page 목적지가 지정되지 않은 새 문서는 `pages:write-page`의 기본 목적지 규칙을 따른다. Markdown 파일을 명시적으로 요청받으면 해당 파일을 만든다.
- Page와 로컬 사본을 둘 다 둘 때는 어느 쪽이 기준인지, 사본은 언제의 기록인지 명시한다. 자동 동기화를 약속하지 않는다.
- 저장 후 다시 읽어 제목·섹션 순서·체크 상태·현재 및 다음 CP를 확인한다. 출력 도구가 미리보기를 제공하면 화면도 확인하고, 확인하지 못한 화면을 검수 완료로 보고하지 않는다.
- 최종 응답에는 문서 링크, 현재 CP, 다음 CP와 필요한 미확인 사항만 간단히 알린다.
