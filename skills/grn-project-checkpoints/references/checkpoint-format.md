# 체크포인트 형식

새 CP를 만들 때 아래 구성을 작업 규모에 맞게 적용한다. 중괄호 안은 작성할 값이며 완성 문서에 남기지 않는다. 단계 수와 항목 수는 고정하지 않는다.

## 상단 배치

네이티브 제목은 `{프로젝트명} 작업 체크포인트`로 하고 본문 첫 줄에 같은 제목을 반복하지 않는다. 목적과 현재 구현 범위를 한 문단으로 설명한다.

ChatGPT Page에서는 다음 네이티브 callout을 사용할 수 있다. 다른 파일 형식에서는 지원되는 일반 문단이나 인용문으로 바꾼다.

```markdown
> [!CALLOUT] 📌
>
> **현재 상태: {현재 CP와 확인한 범위}**
>
> **다음 작업: {다음 CP와 구체적인 결과}**
>
> 갱신 기준일: {날짜}
```

주요 섹션은 H1을 사용한다. 필요한 하위 설명만 H2로 나눈다.

```markdown
# 진행 현황

| CP | 작업 범위 | 상태 |
|---|---|---|
| CP1 | {첫 결과} | {완료 또는 현재 상태} |
| CP2 | {다음 결과} | {대기 또는 진행 중} |
```

상태의 기본 어휘는 **대기·진행 중·검증 대기·완료**다. `다음 작업`은 상태와 별도로 표시할 수 있다. 진행표와 callout은 체크박스 편집만으로 자동 갱신되지 않으므로 문서 수정 때 함께 확인한다. 진척률은 항목 크기가 다르면 오해를 줄 수 있어 기본으로 넣지 않는다.

## CP 단위

다음 틀을 각 단계에 반복한다. 체크리스트는 코드 블록에서 꺼내 실제 편집 가능한 항목으로 저장한다. 초안의 체크 상태는 근거에 맞춰 정한다.

```markdown
# CP1 {구체적인 작업 범위}

{이 단계가 최종 구조에 남기는 책임·계약·기능과 필요한 이유를 한두 문장으로 설명한다.}

- [ ] {구현 또는 결정할 결과}
- [ ] {그 결과를 확인할 실행이나 검사}

**완료 기준:** {관찰 가능한 통과 조건}

**검증 기록:** {확인한 경우 날짜·환경·결과·근거 위치}
```

후속 CP에서 핵심 소유권이나 API를 다시 절개해야 하는 임시 구현은 독립 CP 결과로 두지 않는다. 확정된 후속 요구를 반영한 구조 단계를 먼저 정의하고, 각 CP는 그 구조의 한 층을 구현·검증한다.

다음 두 결과는 별개의 항목이다.

- `- [x] C++ 환경 어댑터 구현과 소스 검토`
- `- [ ] UE 빌드·PIE에서 관측부터 보상까지 반복 실행`

소스만 확인했다면 전체 CP를 완료로 표시하지 않는다. 단, 해당 CP의 목적 자체가 설계나 소스 검토라면 그 목적에 맞는 완료 기준을 사용한다.

## 선택 섹션

- **구조 방향:** 구현 소유권이나 데이터 흐름이 단계 구분을 이해하는 데 필요할 때 짧은 설명·표·텍스트 도식을 둔다. 계획을 확정된 구현처럼 서술하지 않는다.
- **검증 기록:** 여러 CP에서 공통으로 참조하는 결과가 많으면 별도 표로 모으고 날짜·환경·검증 층을 함께 적는다.
- **후속 확장:** 초기 실행 경로에 필수가 아닌 항목을 둔다. 해당 요구가 정해지면 별도 CP로 구체화한다.
- **설계와 근거:** 관련 설계 Page, 코드 위치, 실행 기록을 연결한다. 로컬 파일은 실제 경로를 사용하고 공개 Git URL을 만들지 않는다.
